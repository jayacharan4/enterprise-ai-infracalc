Model Weight Memory
How many GB the model weights occupy in GPU memory at the selected numerical precision
Weight_Memory_GB = Params_B × BytesPerParam BytesPerParam: BF16/FP16 = 2 | FP8/INT8 = 1 | INT4 = 0.5
Why it works: At BF16 precision, every single model parameter is stored as a 2-byte floating-point value. With 70 billion parameters, that is 70B × 2 bytes = 140 billion bytes = 140 GB. The ×10⁹ and ÷10⁹ factors cancel perfectly, leaving a clean GB result.
Step-by-Step Calculation
Params_B = 70 BytesPerParam = 2 (BF16) Weight_Memory_GB = 70 × 2 = 140 GB

2
KV Cache Memory
Memory required to hold the key-value attention tensors for all in-flight inference requests simultaneously
KV_Cache_GB = 2 × Layers × KVHeads × HeadDim × EffectiveContextLen × ConcurrentReqs × KVBytesPerElement / 1e9 EffectiveContextLen = (InputTokens + OutputTokens) × ConversationDepth ConversationDepth = 1 for stateless/single-turn workloads (RAG, batch, summarization) ConversationDepth > 1 for multi-turn chat: each user slot accumulates KV cache across turns The "2×" represents the Key tensor + the Value tensor (both must be stored)
Why it works: During inference, the transformer caches Key and Value tensors for every attention layer, every token position in the active context, and every concurrent request. This avoids recomputing past attention on each new token. The total memory grows proportionally with depth (layers), attention head configuration (KVHeads × HeadDim), context length, and the number of simultaneous users.

Why ConversationDepth matters: In a multi-turn chatbot, a user on turn 10 has accumulated 10 exchanges worth of tokens in their KV cache slot. A stateless RAG query resets every request. Confusing these two cases is the most common KV cache sizing error — if you size for turn 1 but users average turn 10, your real KV footprint is 10× larger than estimated.
Example A — Stateless (RAG / Batch), ConversationDepth = 1
InputTokens = 512 OutputTokens = 256 ConversationDepth = 1 (single-turn, context resets each request) EffectiveContextLen = (512 + 256) × 1 = 768 tokens KV_Cache_GB = 2 × 80 × 8 × 128 × 768 × 32 × 2 / 1,000,000,000 = 8,053,063,680 / 1,000,000,000 ≈ 8.05 GB
Example B — Multi-Turn Chat, ConversationDepth = 10
InputTokens = 512 (per turn) OutputTokens = 256 (per turn) ConversationDepth = 10 (avg user is mid-conversation, 10 turns accumulated) EffectiveContextLen = (512 + 256) × 10 = 7,680 tokens KV_Cache_GB = 2 × 80 × 8 × 128 × 7,680 × 32 × 2 / 1,000,000,000 = 80,530,636,800 / 1,000,000,000 ≈ 80.5 GB (10× larger than the stateless case)

Always set ConversationDepth to your expected average session depth, not best-case turn 1.
3
Total Required Memory
Full GPU memory footprint including a headroom buffer for the ML framework, CUDA runtime, and activation memory
Total_Required_GB = (WeightMem + KVCacheMem) × (1 + OverheadFraction) OverheadFraction default = 0.08 (8%) Overhead covers: CUDA runtime, framework buffers, activations, OS-level allocs
Step-by-Step Calculation
WeightMem = 140.00 GB KVCacheMem = 8.05 GB OverheadFraction = 0.08 (8%) Total_Required_GB = (140.00 + 8.05) × (1 + 0.08) = 148.05 × 1.08 ≈ 159.9 GB
4
Minimum GPU Count (Memory-Bound)
The fewest GPUs needed to physically fit the model and KV cache in VRAM before redundancy is applied
Available_Per_GPU = GPU_VRAM × UtilizationTarget Min_GPUs_Raw = CEIL(Total_Required_GB / Available_Per_GPU) Min_GPUs = MAX(Min_GPUs_Raw, TensorParallelDegree)
Why the utilization cap? Capping at 85% prevents out-of-memory (OOM) errors under burst traffic, temporary allocation spikes, and framework overhead growth. Running GPUs at 100% VRAM fill is a recipe for crashes.
Step-by-Step Calculation
GPU_VRAM = 192 GB (MI300X) UtilizationTarget = 0.85 (85%) Available_Per_GPU = 192 × 0.85 = 163.2 GB Min_GPUs_Raw = CEIL(159.9 / 163.2) = CEIL(0.98) = 1 GPU Min_GPUs = MAX(1, 1) = 1 GPU (tensor parallel = 1)
✅ This is the MI300X advantage: Its 192 GB HBM3 capacity fits the entire Llama 3 70B model on a single card at BF16, eliminating the inter-GPU communication overhead that tensor parallelism introduces. The H100 (80 GB) would require a minimum of 2 GPUs just to store the weights.
5
Recommended GPU Count & Server Count
Production-ready GPU count after applying redundancy for HA, fault tolerance, and traffic burst headroom
Recommended_GPUs = CEIL(Min_GPUs × RedundancyFactor) Servers = CEIL(Recommended_GPUs / GPUsPerServer) Total_VRAM = Recommended_GPUs × GPU_VRAM
Step-by-Step Calculation
Min_GPUs = 1 RedundancyFactor = 1.25 (N+25% spare capacity) Recommended_GPUs = CEIL(1 × 1.25) = CEIL(1.25) = 2 GPUs Servers = CEIL(2 / 8) = CEIL(0.25) = 1 server Total_VRAM = 2 × 192 = 384 GB available

Output Throughput — Tokens/sec
How many output tokens per second the full system can generate across all concurrent requests
TPS_per_GPU = (GPU_BW_TBs × 1e12) / (2 × Params_B × 1e9) × EfficiencyFactor Total_TPS = TPS_per_GPU × Recommended_GPUs Decode is memory-bandwidth-bound: each token requires reading all weights once from HBM Efficiency factor (0.35) accounts for batching overhead, memory ops, and practical MFU
Why memory bandwidth — not TFLOPS — drives decode throughput: At production batch sizes, generating each new output token requires reading the entire set of model weights from HBM memory exactly once. The GPU's compute cores finish their work faster than memory can deliver the next weights, making bandwidth the bottleneck. Throughput = how fast you can stream weights ÷ how many weights you need per token.
Step-by-Step Calculation
GPU_BW_TBs = 5.3 TB/s (MI300X) Params_B = 70 billion EfficiencyFactor = 0.35 (35% practical MFU) TPS_per_GPU = (5.3 × 1e12) / (2 × 70 × 1e9) × 0.35 = 5,300,000,000,000 / 140,000,000,000 × 0.35 = 37.86 × 0.35 ≈ 13.25 tok/s per GPU Total_TPS = 13.25 × 2 ≈ 26.5 tok/s (system-wide)
📊 The 0.35 efficiency factor is conservative. Optimised runtimes like vLLM with continuous batching or SGLang with RadixAttention can achieve 40–50% MFU for suitable workloads, boosting effective TPS by up to 40% over this estimate.
7
Time to First Token (TTFT)
User wait time from prompt submission to receiving the very first output token — the prefill latency
TTFT_ms = (InputTokens × 2 × Params_B × 1e9) / (GPU_TFLOPS × 1e12 × Efficiency × NumGPUs) × 1000 Numerator: total FLOPs to process the input prompt (~2 FLOPs per weight per token) Denominator: available compute throughput of the GPU cluster
Why TTFT uses TFLOPS not bandwidth: The prefill (processing the input prompt) is compute-bound, not bandwidth-bound. Unlike decode, prefill processes all input tokens in a single forward pass with large matrix multiplications that fully saturate the GPU's compute units. So TFLOPS — not memory bandwidth — is the limiting factor.
Step-by-Step Calculation
InputTokens = 512 Params_B = 70 GPU_TFLOPS = 1,307 (MI300X BF16) Efficiency = 0.35 NumGPUs = 2 Numerator = 512 × 2 × 70 × 1e9 = 71,680,000,000,000 FLOPs Denominator = 1,307 × 1e12 × 0.35 × 2 = 914,900,000,000,000 FLOPs/sec TTFT_s = 71,680,000,000,000 / 914,900,000,000,000 = 0.0784 s TTFT_ms = 0.0784 × 1000 ≈ 78 ms
8
Time per Output Token (TPOT)
Time between each successive output token after the first — determines the perceived "typing speed" of the model
TPS_per_Request = Total_TPS / ConcurrentRequests TPOT_ms = 1000 / TPS_per_Request
Why throughput is divided by concurrency: The system's total token output is shared proportionally across all simultaneous request streams. Each individual user gets their slice of the total system bandwidth.
Step-by-Step Calculation
Total_TPS = 26.5 tok/s ConcurrentRequests = 32 TPS_per_Request = 26.5 / 32 = 0.828 tok/s TPOT_ms = 1000 / 0.828 ≈ 1,207 ms/token
⚠️ 1.2 seconds per token is slow for a chatbot (where users expect ~50–100 ms/token). To achieve 100 ms TPOT at 32 concurrent users, you need Total_TPS ≥ 320 tok/s — roughly 12× more GPU capacity. This is why the tool fires a latency warning and recommends additional GPU servers.
9
End-to-End Latency
Total wall-clock time from prompt submission to completed response — the full user experience latency
E2E_Latency_ms = TTFT_ms + (OutputTokens × TPOT_ms)
Step-by-Step Calculation
TTFT_ms = 78 ms OutputTokens = 256 TPOT_ms = 1,207 ms E2E_Latency_ms = 78 + (256 × 1,207) = 78 + 308,992 ≈ 309,070 ms (≈ 309 seconds)
💡 309 seconds is extremely slow — the tool's "> 5 second" alert fires immediately. The fix is more GPUs (reducing TPOT) or fewer concurrent users. Scaling from 2 → 16 GPUs would reduce TPOT by 8× to ~151 ms/token and E2E to ~39 seconds — still long for chat, but fine for batch summarization.

Tokens/sec/Watt — Energy Efficiency
Output throughput normalized by total cluster power draw — the energy efficiency of the inference system
Total_Power_W = Recommended_GPUs × GPU_TDP_W TPS_per_Watt = Total_TPS / Total_Power_W
Step-by-Step Calculation
Recommended_GPUs = 2 GPU_TDP = 750 W (MI300X) Total_Power_W = 2 × 750 = 1,500 W TPS_per_Watt = 26.5 / 1,500 ≈ 0.0177 tok/s/W
⚡ Use this metric in the Compare Hardware mode to identify which GPU platform delivers the most throughput per watt — critical for data center power budget planning and sustainability reporting. A higher number is always better.

Actual per-instance hourly cost after applying pricing model discounts and negotiated enterprise agreements

21
Break-Even Point
Months until cumulative on-premises cost equals cumulative cloud cost — after this point, on-prem is cheaper
Monthly_Savings = Cloud_Monthly − OnPrem_Monthly_OpEx Break_Even_Months = HW_CapEx / Monthly_Savings Only applies when Cloud monthly rate > On-Prem monthly OpEx Before break-even: cloud is cheaper | After break-even: on-prem is cheaper
Why it works: On-prem has a large upfront CapEx but lower ongoing monthly costs. Cloud has zero CapEx but high monthly rates. Every month, the difference between cloud's monthly rate and on-prem's lower OpEx chips away at the initial hardware investment. Break-even is when those accumulated savings fully pay back the CapEx.
Step-by-Step Calculation
Cloud_Monthly = $181,865 OnPrem_Monthly_OpEx = $388,229 / 12 = $32,352 Monthly_Savings = $181,865 − $32,352 = $149,513 / month Break_Even_Months = $880,000 / $149,513 ≈ 5.9 months ← on-prem pays itself back in under 6 months
✅ Strong case for on-premises: At 100% utilization and these assumptions, the capital investment is recovered in under 6 months. Over 3 years, on-prem avoids approximately $4.5M in cloud spend. The tool highlights this with a green success alert when break-even is under 18 months.
22
Savings Percentage
The relative cost difference between the two options, expressed as a percentage of the more expensive option
Savings_Pct = ((Total_Cloud − Total_OnPrem) / Total_Cloud) × 100 Positive value = on-prem is cheaper | Negative value = cloud is cheaper
Step-by-Step Calculation
Total_Cloud = $6,547,134 Total_OnPrem = $2,044,687 Savings_Pct = (($6,547,134 − $2,044,687) / $6,547,134) × 100 = ($4,502,447 / $6,547,134) × 100 ≈ 68.8% ← on-prem is 68.8% cheaper over 3 years
📊 This flips dramatically if utilization drops. At 20% GPU utilization (4.8 hrs/day), cloud annual compute drops to ~$434K/yr while on-prem OpEx remains fixed at $388K/yr — making cloud slightly cheaper at that scale. The tool's cumulative cost chart lets you see exactly where the crossover occurs.

On-Premises $/GPU-Hour
The fully-loaded cost per GPU-hour when owning infrastructure — CapEx and all OpEx amortized across every GPU-hour in the analysis period
GPU_Hours_In_Period = NumGPUs × Years × 8,760 OnPrem_Per_GPU_Hour = Total_OnPrem_TCO / GPU_Hours_In_Period Numerator: the COMPLETE TCO — hardware purchase, power, personnel, maintenance, software Denominator: every GPU-hour available, running 24×7 for the full analysis period
Why this metric matters: The headline TCO number ($2M vs $6.5M) is hard to compare across different cluster sizes. $/GPU-hour normalizes for scale — a 10-GPU cluster and a 100-GPU cluster can be compared on equal footing. It is the on-premises equivalent of what cloud providers publish as their list price.
Step-by-Step Calculation
Total_OnPrem_TCO = $2,044,687 NumGPUs = 32 Years = 3 Hours/year = 8,760 GPU_Hours_In_Period = 32 × 3 × 8,760 = 32 × 26,280 = 840,960 GPU-hours OnPrem_Per_GPU_Hour = $2,044,687 / 840,960 ≈ $2.43 / GPU-hour
💡 Key insight: This $2.43/GPU-hr includes the full hardware purchase price spread across 3 years. If you extend the analysis to 5 years using the same hardware, the GPU-hours in the denominator grow while the CapEx stays fixed — the effective $/GPU-hr falls. Longer ownership periods always lower the on-prem unit cost.

The effective per-GPU hourly rate from the cloud provider — a contract rate independent of actual utilization
Cloud_Per_GPU_Hour = Effective_Hourly_Rate / GPUs_Per_Instance Effective_Hourly_Rate already accounts for reserved pricing and enterprise discounts (Formula 16) This number does NOT change with utilization — you pay it whether the GPU is busy or idle
Why cloud $/GPU-hr is a fixed rate: Cloud instances are billed by the hour regardless of how hard the GPU works. At 20% utilization you still pay $61.94/hr for the instance. The $/GPU-hr metric therefore represents your minimum committed spend — actual cost-per-useful-token rises as utilization falls.
Step-by-Step Calculation
Effective_Hourly_Rate = $61.94 / hr / instance (from Formula 16) GPUs_Per_Instance = 8 Cloud_Per_GPU_Hour = $61.94 / 8 = $7.74 / GPU-hour

Annual Token Output
How many tokens the deployment generates per year — the denominator shared by both $/1M token formulas
System_TPS = TPS_per_GPU × NumGPUs (from Formula 6) Annual_Tokens = System_TPS × 3,600 × 8,760 × Utilization% 3,600 = seconds per hour | 8,760 = hours per year Utilization% is the same value used for cloud compute cost — ensures apples-to-apples comparison
Why the same utilization % for both on-prem and cloud: To compare on-prem and cloud $/1M tokens fairly, both must assume the same workload intensity. If you ran on-prem at 100% and cloud at 50%, the per-token costs would be incompatible. Using a single utilization figure ensures the token denominator is identical — the only difference is the cost numerator.
Step-by-Step Calculation
TPS_per_GPU = 13.25 tok/s (from Formula 6) NumGPUs = 32 Utilization = 1.00 (100%, 24×7) System_TPS = 13.25 × 32 = 424 tok/s Annual_Tokens = 424 × 3,600 × 8,760 × 1.00 = 424 × 31,536,000 = 13,371,264,000 tokens/yr ≈ 13.37 billion tokens/yr (13,371M tokens)
⚡ At 50% utilization the annual token output halves to ~6.69 billion tokens/yr. Since the annual cost does not halve (on-prem fixed costs remain constant), $/1M tokens roughly doubles at 50% utilization. This is exactly what the Sensitivity Analysis card in the TCO Calculator shows.

On-Premises $/1M Tokens
The fully-loaded cost to generate one million output tokens from owned infrastructure — the CFO-facing unit economics metric for on-prem
Annual_OnPrem_Cost = Total_OnPrem_TCO / Years OnPrem_Per_M_Tokens = Annual_OnPrem_Cost / (Annual_Tokens / 1,000,000) Equivalent form: (Total_OnPrem_TCO / Years) × (1,000,000 / Annual_Tokens) Annual_Tokens from Formula 25 — must use same utilization as cloud
Why annualize rather than use the full TCO period? Dividing by years normalizes the cost to a single year of operation, making it directly comparable to cloud's annual run rate. Using the raw 3-year total would produce an identical result, but the year-by-year framing is cleaner for budget discussions.
Step-by-Step Calculation
Total_OnPrem_TCO = $2,044,687 Years = 3 Annual_Tokens = 13,371,264,000 (13,371M tokens, from Formula 25) Annual_OnPrem_Cost = $2,044,687 / 3 = $681,562 / year OnPrem_Per_M_Tokens = $681,562 / (13,371,264,000 / 1,000,000) = $681,562 / 13,371 ≈ $0.051 / 1M tokens (~$0.05/1M)

Cloud $/1M Tokens
The cost to generate one million output tokens using cloud GPU instances — using the annual run rate as the cost basis
Annual_Cloud_Cost = Annual_Compute + Annual_Ancillary (Formulas 18 + 19) Cloud_Per_M_Tokens = Annual_Cloud_Cost / (Annual_Tokens / 1,000,000) Annual_Tokens from Formula 25 — identical to the on-prem denominator for fair comparison Unlike on-prem, cloud annual cost itself falls at lower utilization (fewer compute hours billed)
Why cloud $/1M tokens is more stable under utilization changes: When utilization drops, both the numerator (cloud compute cost) and the denominator (tokens produced) fall proportionally for compute. Ancillary costs (storage, egress, support) stay fixed — so cloud $/1M tokens rises slightly at low utilization but far less dramatically than on-prem.
